# Architecture and Product Decisions

| ID | Decision | Status | Rationale / notes |
|---|---|---|---|
| D-001 | Internal manager/employee app, not public booking marketplace | Accepted | Matches operating model |
| D-002 | Moroccan market; MAD default currency | Accepted | Display defaults configurable |
| D-003 | Phone and desktop uploads from first release | Accepted | Both workflows required |
| D-004 | OCR classification/extraction with mandatory human review | Accepted | Sensitive data needs verification |
| D-005 | Early practical MVP, then incremental delivery | Accepted | Deliver core first in small testable slices |
| D-006 | WhatsApp files manually downloaded and batch-uploaded initially | Accepted | API deferred |
| D-007 | Product identity separate from configurable company identity | Accepted | Company can change branding |
| D-008 | Fleetora is a provisional working name only | Provisional | Final name/trademark/domain check pending |
| D-009 | React + TypeScript, Node.js + Express, PostgreSQL | Proposed — implemented in slice 1 | Slice 1 runs on Node 22, Express 5, PostgreSQL 16, React 19 + Vite; confirm at slice review |
| D-010 | File storage and OCR behind replaceable adapters | Accepted direction | Avoid vendor lock-in |
| D-011 | No production deployment until security, backup and tests pass | Accepted | Release safety gate |
| D-012 | Production is hosted on a dedicated company computer/server; database and private documents remain inside the company | Accepted direction | Remote access through approved VPN; no direct public exposure |
| D-013 | Current Intel i5-650 / 8 GB / 512 GB SSD computer is for development and testing only | Accepted | Do not use for real customer records or production 24/7 |
| D-014 | Production host target is a newer machine with at least 16 GB RAM and SSD; 1 TB preferred | Accepted target | Final CPU/OS selection depends on company IT and budget |
| D-015 | Signed paper contract remains the official executed contract in the initial release; PDF is for preview, printing and archiving | Accepted | Electronic signature deferred pending legal/business validation |
| D-016 | Initial WhatsApp reminders use prefilled wa.me links; employee reviews and sends manually | Accepted | No automated sending or Business API in initial release |
| D-017 | Phone uploads inside company use Wi-Fi; remote phone uploads use company-approved VPN | Accepted direction | Secure access to the same company-hosted application |
| D-018 | OCR evaluation uses 20–30 representative permitted/minimized samples before provider selection | Accepted | Measure Arabic/French accuracy, cost, latency and privacy |
| D-019 | Passwords hashed with scrypt (Node built-in), parameters stored per hash | Proposed (2026-11-02) | No native build tools on Windows; memory-hard; can be raised later with transparent rehash on login |
| D-020 | Database-backed opaque sessions in an HttpOnly SameSite=Strict cookie, not JWT | Proposed (2026-11-02) | Immediate server-side revocation on logout, deactivation, role or password change |
| D-021 | Local development does not require Docker; native Node.js + PostgreSQL | Proposed (2026-11-02) | Simplest reliable setup on the i5-650 / 8 GB Windows 11 test PC |
| D-022 | One role per user (manager/employee) mapped to a role→permission table; API checks permissions, not role names | Proposed (2026-11-02) | Lets roles change or branch scoping be added without rewriting route checks |
| D-023 | Audit log is append-only at database level; users are deactivated, never hard-deleted | Proposed (2026-11-02) | Traceability; trigger blocks UPDATE/DELETE/TRUNCATE on audit_logs |
| D-024 | Ease of use and a modern, elegant interface understandable by Moroccan staff is a release requirement for every screen | Accepted (2026-11-02, owner) | Rules in `docs/UX_GUIDELINES.md`; acceptance criterion 29 |
| D-025 | GitHub Actions CI runs typecheck, lint, all tests, migration check and build on feature/fix branches and on PRs to main | Accepted (2026-11-02, owner) | Quality checks only: no deployment, no secrets, disposable PostgreSQL service; test-database safety guards are not relaxed |
| D-026 | Multi-branch from day one: branches table; every vehicle belongs to a branch; employees see only their assigned branches; managers (branches.all) see all; one scope helper for every branch-owned query | Accepted (2026-11-02, owner answers BR-02) | Customers stay company-wide; pickup and return branches will be separate fields on reservations/contracts |
| D-027 | Permissions = role permissions + individual grants; only permissions marked delegable can be granted, and only by a user who holds them; effective permissions are read from the database on every request, so changes apply immediately | Accepted (2026-11-02, owner answer BR-14) | Grants and branch assignments are audited (who, to whom, before/after, when) |
| D-028 | Vehicle lifecycle stores physical state only; "reserved" is derived from bookings. Return → inspection pending; inspection → available or maintenance; maintenance → inspection pending; unblock → inspection pending; retire only from out of service. Enforced by a transitions table + database trigger + compare-and-set, with append-only history | Accepted (2026-11-02, owner + reviewed amendments) | Check-out/check-in transitions are reserved for the rental workflow (slice 4); retire will also check future allocations once reservations exist |
| D-029 | Tests run on a fresh per-run database; a run can only wipe the database it created. seed:dev fills only an empty development database, never changes existing accounts; no marker can bypass these checks | Accepted (2026-11-02, review) | Replaces the earlier marker-based approach |
| D-030 | Public demo on Railway (Hobby), deployed from the local working tree with `railway up`; FICTITIOUS DATA ONLY; login required; private PostgreSQL; not a production system | Accepted (2026-11-02, owner) | Real company data stays on the company host (D-012). Setup: `.railway/railway.ts`, `docs/RAILWAY_DEMO.md`; demo data only through the guarded `seed:demo` |
| D-031 | Uploaded files: metadata in `stored_files`, bytes in private storage behind the `FileStorage` adapter under a content-addressed random key; type decided from the file's bytes (JPEG, PNG, WebP, PDF only); originals immutable and never deleted (documents and photos are archived, not removed); upload as raw request body, one file per request | Proposed (2026-11-03, slice 2b) | Retry-safe phone uploads, no client paths or names trusted; replacing local disk later needs only a new adapter. On Railway the storage folder must be a mounted volume |
| D-032 | Vehicle document status is computed, not stored: expired before today, expiring within 30 days, on the Africa/Casablanca calendar; alerts are on-screen only (no automatic messages) | Proposed (2026-11-03, slice 2b) | Always consistent with the dates; the 30-day window can become a company setting later |
| D-033 | Customers are company-wide; duplicates are signals (same phone key, ID number key or licence number) shown before saving and confirmed by staff, never unique constraints and never merged automatically; merging stays a reviewed manager action (F-023) | Proposed (2026-11-04, slice 2c) | Follows spec §5; avoids blocking families sharing a phone |
| D-034 | Customer scans are reviewed by a person with `customers.verify` (no OCR in this release); review status pending / verified / rejected (reason required); scans are archived, never deleted | Proposed (2026-11-04, slice 2c) | OCR (F-011) will only add suggestions to this review; no external provider without approval |
| D-035 | Business records are never deleted: database triggers refuse DELETE/TRUNCATE on business tables; corrections are archive / deactivate / cancel with reason; history tables are append-only | Accepted (2026-11-04, owner: data must never be lost) | Applies to all later tables (contracts, payments, deposits…) |
| D-036 | Reservation overlap is prevented by a PostgreSQL exclusion constraint on (vehicle, period) for active statuses; times are entered and shown in Africa/Casablanca and stored as timestamptz; days = ceil(duration / 24 h); money is integer centimes of MAD | Proposed (2026-11-04, slice 3) | Concurrency-safe; extra day for late returns stays a manager decision at check-in (BR-05) |
| D-037 | Backups = pg_dump custom dump + copy of every stored file + manifest with SHA-256; restore only into an empty database and proven by counts and checksums; nightly backup, weekly off-site encrypted copy, monthly restore drill (schedule to confirm) | Proposed (2026-11-04, slice 3) | See `BACKUP_RESTORE.md`; on the company host only (D-012) |
| D-038 | Company data stays inside the company system: no analytics, telemetry, external OCR or third-party scripts; a test fails if outbound network code is added | Accepted (2026-11-04, owner) | Any future integration needs explicit approval and a privacy review |
| D-039 | Contract wording belongs to each company: the template (title, handed documents, clause, general conditions) is edited in the app; every save is a new immutable version and each contract keeps its version and a frozen copy of the printed data | Accepted (2026-11-04, owner BR-17) | Old contracts never change when the template or a customer record changes |
| D-040 | Money movements are an append-only ledger per contract; corrections are reversal entries; deposits (cash, cheque, card hold, transfer) are tracked apart from rent and leave only by refund or by a "kept" entry with reason and right | Proposed (2026-11-04, slice 4) | Basis for cash closing and reports (slice 5) |
| D-041 | The printable contract is an HTML page with print CSS; the PDF comes from the browser's "Save as PDF". No server-side PDF engine for now | Proposed (2026-11-04, slice 4) | No extra dependency; layout checked as a 2-page A4 PDF in Chromium. A server PDF can be added later if archiving needs it |
| D-042 | Late return: proposed extra days = ceil(late / 24 h) once the delay exceeds the company tolerance (default 60 min); only a `pricing.change` holder may charge a different number, with a reason | Proposed (2026-11-04, BR-05) | Never charged silently; shown before confirming the return |

New decisions include date, status, context and impact. Supersede decisions rather than silently rewriting history. A Proposed or Accepted direction is not a claim that infrastructure has already been deployed.
